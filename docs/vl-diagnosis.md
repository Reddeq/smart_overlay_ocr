До живых тестов основной рабочей гипотезой была сложность общего задания и полного учёта ID при схеме, допускающей пустоту. B/C показали дополнительную проблему: даже компактный дифференциальный запрос с пятью OCR даёт неверные объединения. F показал формально корректное перечисление строк без смыслового объединения. Поэтому масштаб и требование перечислить все ID не объясняют ошибки целиком. Для пустого Analysis гипотеза сложности остаётся непроверенной; для группировки подтверждён неверный результат модели при всех трёх проверенных вариантах запроса. Единственный пример в текущем production-промпте показывает одиночную группу: возможное влияние такого примера на F — гипотеза, а не установленная причина.

## Изолированная команда

По умолчанию команда только строит план. Используются синтетические изображения и OCR с известным правильным ответом; OCR-движок, уточнения и экспорт не запускаются. `--project` используется только для явно выбранных F-project/X-project; файл открывается для чтения и не сохраняется.

| Тест | Проверка | Запросов |
|---|---|---:|
| A | Точный JSON status=ok, value=123 без изображений | 1 |
| B | 5 строк: одна трёхстрочная надпись и две независимые соседние подписи | 1 |
| C | Тот же запрос B плюс один небольшой исходный рисунок | 1 |
| V | Прочитать TEST 123; ожидаемый текст отсутствует в промпте и схеме | 1 |

| E | 5/10/20/40/80 фрагментов, полный список групп против только объединений; без изображений | До 10, выбор `--sizes` / `--scale-mode` |

Синтетические случаи детерминированы; у каждой пятёрки первые три строки образуют одну подпись, две другие подписи находятся в отдельных колонках на одной высоте. Оценка требует точной группировки и порядка строк, запрещает неизвестные/повторные ID и объединение соседних независимых подписей. Для F отдельно проверяется полнота **самого ответа**, до локального восстановления пропусков. Для пользовательского проекта без разметки-эталона можно проверить геометрию и ссылки, но правильность группировки обозначается `unverified` и требует просмотра.

В F сохранён production-промпт без изменений; для всех экспериментов отключён stream и задан диагностический выходной лимит (по умолчанию 1024). На большом проекте или E-full при `finish_reason=length` нужен отдельный осознанный запуск с достаточным бюджетом; такое завершение не доказывает неспособность группировать. Тайм-ауты основного приложения не меняются. Кеш ответов основного приложения не читается и не записывается.

Фактический provider сохраняется, только если API вернул его; неизвестное значение не угадывается. Формат Chat Completions с image_url и base64 сверён с [официальной документацией изображений](https://openrouter.ai/docs/guides/overview/multimodal/image-understanding).

## Бюджет и результаты

Перед отправкой проверяются точное подтверждённое число запросов, максимальное число запросов, сумма выходных лимитов и размер каждого запроса. По умолчанию максимум 8 запросов, 8192 выходных токена суммарно и 4 МиБ на запрос. Это ограничивает серию, **но не является долларовым лимитом**: входные токены тоже оплачиваются, цены и работа сервера после тайм-аута зависят от API. Для денежного потолка следует использовать ключ с лимитом расходов на стороне API. Никаких повторных генераций после сетевой ошибки или невалидного JSON нет.

Для каждого запроса в JSON записываются модель/формат/запрошенный и фактический провайдер, число OCR и изображений, байты/хеш запроса, аудит изображений, HTTP-код, finish_reason, токены и стоимость при наличии, время, полный очищенный текст ответа и результаты проверки JSON/схемы/содержания. В Markdown находится сравнительная таблица. Отчёты сохраняются после каждого запроса, в том числе при досрочной остановке.

В консоль выводятся только размеры и статусы. Запрос, исходные OCR-тексты, изображения, ключи и заголовки не сохраняются. Текст ответа может содержать цитаты документа — JSON отчёта следует считать приватным. Повторённые моделью ключи/authorization/data URL очищаются. В план и журнал попадают только MIME, размеры и SHA-256 изображений; локальная проверка декодирует base64 со строгой проверкой, сверяет сигнатуру/MIME и проверяет PNG/JPEG средствами Pillow. Это доказывает корректность локальной упаковки, а способность модели прочитать картинку проверяет только живой V.

Классы `empty_http_response`, `empty_message_content`, `invalid_json`, `valid_json_empty`, `valid_content`, `incorrect_grouping` различаются. Ошибки оболочки API/схемы/HTTP/транспорта и неизвестная правильность пользовательской группировки выделены отдельно. Обрезание видно по `finish_reason`, даже если JSON не удалось разобрать. `null` означает, что метрика неизвестна, а не ноль.

## Решение после получения ответов

Фактические B/C/F **не подтверждают** пользу одной лишь замены полного формата на дифференциальный: B/C уже используют только merges и тоже неверны. Увеличение тайм-аутов или повторов не устраняет показанную ошибку содержания. Запрет пустых массивов сам по себе тоже не решает проблему: F непустой и полностью учитывает ID, но группирует неверно.

Конкретный кандидат на исправление для отдельного эксперимента — добавить в узкий промпт группировки положительный пример объединения трёх строк и отрицательный пример независимых подписей на одной высоте, вместо единственного примера одиночной строки. Если это не даёт правильных ответов на исходном и отдельном контрольном примере, корректность результата для выбранной модели/провайдера всё ещё не подтверждена. Изменение промпта не объявляется исправлением до живого сравнения; в основной Smart OCR оно сейчас не внесено. Кропы/локальные кандидаты и разделение табличного и текстового задания могут быть дальнейшими вариантами, но архитектура в рамках этого исследования не меняется.

Если не проходит B — сначала проверять способность модели/провайдера выполнить простое объединение. Если B проходит, а V не проходит, сначала исследовать зрительный тракт. Если результат меняется только в D — разбирать response_format и поддержку endpoint. Если поведение меняется только при закреплении провайдера — фиксировать эту зависимость на повторяемом наборе, без вывода о всех провайдерах.

Критерий завершения исследования полностью **не достигнут**: получены реальные A/B/C/V/F и показана ошибка группировки на пяти OCR, но порог и причина возникновения пустого Analysis на большом документе не определены. Целиком правильного ответа на группировку нет ни в B, ни в C, ни в F. Подготовлены CLI и отчёт, локальный аудит и автоматические тесты; живые ответы не подменяются. Основной OCR, редактор, таблицы и генератор PPTX в рамках этой задачи не изменены. После чтения пользовательских отчётов новых платных запросов агент не выполнял. Исследование останавливается на этих фактах, без непроверенной смены основной архитектуры.
