# Эксперимент с примерами группировки — 13 ноября 2026

**На прежнем наборе улучшенный промпт дал правильную группировку в B и C. На дополнительном контрольном примере смысловая группировка тоже правильная, но ответ нарушает контракт `merges`, включая одиночный ID.** Это ограниченный положительный результат, а не основание считать задачу решённой для произвольных схем. В основной Smart OCR ничего не интегрировано.

## Условия сравнения

В `smart_overlay/diagnose_vl.py` добавлен вариант `--grouping-prompt examples` с предоставленным пользователем текстом, положительным примером MAXIMUM / OPERATING / PRESSURE и отрицательным примером INLET VALVE / OUTLET VALVE. Подставляется прежний компактный OCR-пакет. Системное сообщение и JSON Schema Merges сохранены.

Модель — `qwen/qwen3-vl-8b-instruct`, фактический провайдер — Parasail. Он закреплён через `order=["parasail"]`, `allow_fallbacks=false`; раньше OpenRouter сам выбрал того же провайдера. Параметры генерации прежние: temperature=0, stream=false, max_tokens=1024, response_format=json_object. Тайм-ауты и основной конвейер не менялись.

До отправки повторно собраны **старые** запросы B/C и проверены их SHA-256 против `outputs/vl-basic.json`:

- B: `80a4d1d152756141828697a315cd890f622633e1fba905e405f3bc66cbbc7cec`.
- C: `6cdf9aa72ec0e7b49926dff3f21f7e57e4e25219d1277576d2a41c08469aed18`.

Это подтверждает неизменность исходных OCR-текстов, координат, ID, упаковки изображения, системного сообщения и параметров генерации перед заменой пользовательского промпта. Изображение C осталось 600×180, PNG, SHA-256 `404f0df3aaea64088ded78fd54a7df8065a9886a161a32f73f5befaa167e34ba`. Эталон не менялся: `[id_1,id_2,id_3]`, `[id_4]`, `[id_5]`.

## Реальные ответы B/C

| Проверка | Старый промпт — реальные merges | Новый промпт — реальные merges | Группировка до → после |
|---|---|---|---|
| B, без изображения | `[[id_1,id_2,id_3],[id_4,id_5]]` | `[[id_1,id_2,id_3]]` | Неверно → верно |
| C, с изображением | `[[id_1,id_3],[id_4,id_5]]` | `[[id_1,id_2,id_3]]` | Неверно → верно |

Оба новых полных ответа одинаковы:

```json
{"merges":[["id_1","id_2","id_3"]] }
```

Состав и порядок трёх строк правильные; независимые VALVE 1 и PUMP 1 не объединены. Все ID известны, повторов и одиночных элементов внутри merges нет. Оценка сделана по точному эталонному разбиению; confidence модель в этом формате не возвращает и в оценке она не используется.

| Старый B | 200 / stop | 412 / 31 | 1.140 | 0.00012625 |

Число выходных токенов уменьшилось, вход увеличился на 425 токенов. Стоимость приведена как её вернул API, без пересчёта по прайсу или вывода о стабильной цене будущих запросов.

## Маршрут и число запросов

Первый прямой POST получил HTTP 403; серия остановилась до C без автоматического повтора. Публичный GET без ключа также вернул 403 `Access denied by security policy`. Ответ модели и usage от этого POST не получены; их отсутствие не выдаётся за нулевую стоимость. Запись этого отказа сохранена отдельно в `outputs/vl-examples.json`.

После **прямого указания пользователя использовать VPN** публичный GET через уже работающий локальный Xray-прокси получил HTTP 200. Затем отдельно запущены ровно два запроса генерации B/C через этот туннель, без повторов. Системные сетевые настройки не изменялись; прокси задавался только процессу запуска. Ключ прочитан из указанного пользователем локального файла, в консоль и отчёты он не выводился.

Результаты успешной серии, полный текст ответов и сравнение со старыми B/C: `outputs/vl-examples-vpn.json` и `outputs/vl-examples-vpn.md`. Старый `outputs/vl-basic.json` не перезаписывался.

## Дополнительный контроль H

После успеха B/C подготовлен и визуально проверен другой синтетический рисунок 760×260 с шестью новыми OCR-фрагментами. Ни тексты, ни ID, ни расположение этого рисунка не совпадают с примерами внутри промпта или исходным B/C:

- Справа сверху: AUXILIARY / POWER / UNIT 27 — одна трёхстрочная надпись, h_1–h_3.
- Слева снизу: SENSOR / PT-408 — одна двухстрочная надпись, h_4–h_5.
- Справа снизу: FUSE F9 — отдельная надпись, h_6.

На **один** дополнительный платный запрос пользователь отдельно дал разрешение. Использован тот же промпт без дополнений под новый рисунок, одна картинка, те же параметры модели и провайдера, лимит 1024 выходных токена, без повторов.

Реальный ответ H:

```json
{"merges":[["h_1","h_2","h_3"],["h_4","h_5"],["h_6"]] }
```

| Что проверяется | Результат |
|---|---|
| Правильные две многострочные надписи | Да |
| Независимая FUSE F9 остаётся отдельно | Да |
| Порядок строк, отсутствие неизвестных/повторных ID | Верно |
| Строгое правило «в merges только два и более ID» | **Нарушено**: присутствует `[h_6]` |
| HTTP / finish_reason | 200 / stop |
| Вход / выход, токены | 1090 / 31 |
| Время / usage.cost | 2.719 с / 0.00029575 |

Поэтому H нельзя называть полностью успешным выполнением инструкции. Семантическое разбиение верно, но строгая проверка ответа не проходит. Исходный текст не исправлялся и не нормализовался для принятия.

В диагностике добавлены раздельные метрики `grouping_valid` и `merge_contract_valid`. При оценке смыслового разбиения одиночная запись рассматривается как отсутствие объединения, но по контракту merges она остаётся ошибкой. Поле `content_valid` и строгий классификатор по-прежнему не принимают такой ответ. Новые метрики дополнительно рассчитаны локально по сохранённым реальным ответам B/C/H, без повторных API-запросов; это отмечено `scoring_replayed_locally`.

Результаты H: `outputs/vl-examples-holdout.json` и `outputs/vl-examples-holdout.md`. Контрольное изображение: `outputs/vl-holdout.png`. Всего через VPN получено три ответа генерации: два из исходного разрешения и один из отдельного разрешения; автоматических повторов не было.

## Вывод и границы

Новый промпт с положительным и отрицательным примерами **помог на проверенном исходном наборе**: B/C стали правильными. Контроль H также дал верные смысловые группы, но показал несоблюдение одного из требований к формату ответа. На этих трёх случаях перенос смысловой группировки выглядит обнадёживающим, надёжность контракта ещё не подтверждена.

Эксперимент сравнивает старый краткий промпт с новым полным текстом пользователя. Он не отделяет вклад самих примеров от более подробных правил нового промпта; по одному запросу на условие также нельзя оценить устойчивость. Причина прежнего пустого Analysis на 205 фрагментах остаётся отдельным неустановленным вопросом. Минимальный Merges и production Analysis — разные задания, поэтому результаты нельзя напрямую переносить на весь Smart OCR.

Production-промпт, `vision.py`, `vision_transport.py`, `pipeline.py`, редактор, OCR, таблицы и PPTX не менялись. Изменения ограничены диагностическим модулем, его тестами и этим отчётом. Дополнительные платные проверки после H не выполнялись.

## Воспроизведение и проверки кода

Без сети можно построить план и проверить исходные хеши:

```powershell
.\.venv\Scripts\python.exe -m smart_overlay diagnose-vl --tests B,C --grouping-prompt examples --model qwen/qwen3-vl-8b-instruct --provider parasail --compare-with outputs\vl-basic.json --max-requests 2 --max-total-output-tokens 2048 --output outputs\vl-examples-plan.json
```

`--execute --confirm-requests 2` превращает этот план в **новую платную серию**; для воспроизведения нужно отдельное решение пользователя. Для H предусмотрен отдельный выбор `--tests H --grouping-prompt examples`; его нельзя включить в серию B/C. Промпт и изображения не сохраняются в сетевой журнал; в отчётах есть ответы модели, параметры, размеры, хеши и результаты проверки.

Прошёл полный набор из **131 теста**. Новые проверки подтверждают неизменность B/C вне текста пользовательского промпта, сверку исходных хешей, ровно два вызова без повторов и автоматического контроля H, отдельный запуск H и различие смысловой правильности и нарушения контракта. Моки проверяют только диагностический код; результаты качества выше основаны на реальных ответах.
